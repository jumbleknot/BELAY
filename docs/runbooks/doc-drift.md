# Doc drift: the doc-impact sweep and the quarterly audit

Keeping an `openwiki/` summary in step with its **source document** is covered by
[the wiki maintenance page](../../openwiki/process/wiki-maintenance.md). Nothing mechanical keeps a
source document in step with **the code it describes**. This runbook covers that direction: docs
from code.

The approach comes from MovieCollectionManager's doc-drift work. Its 2026-11-14 baseline audit found
76 drifts in about 16,800 lines of procedure docs, 4.5 per 1,000 lines. The weak point it measured
was **discovery**, not follow-through: features did 94% of the doc tasks they wrote, and missed the
other documents that named what they changed.

| Layer | When | What it is | Status |
| --- | --- | --- | --- |
| 1. Doc-impact sweep | every SDD feature, at `/speckit-tasks` and at close-out | a required task in the project's tasks template: search the docs for every identifier the feature changes | **live** |
| 2. Mechanical per-PR check | every PR | `describes:` front matter on runbooks, plus a guardrail | **not built**; triggered by step 9 of the audit |
| 3. Drift audit | quarterly | one session reads the procedure docs against the tree, then refreshes the [learnings ledger](../BELAY-Learnings.md) | **live**, procedure below |

## The doc-impact sweep (layer 1)

Every `tasks.md` generated by `/speckit-tasks` carries a **Doc-impact sweep** task in Phase 1 and a
**Close-out re-search** task in the Polish phase. They come from the project override
`.specify/templates/overrides/tasks-template.md`, which Spec Kit resolves ahead of its core template.
The constitution's **Documentation** principle makes the sweep mandatory even when the template is
not used, and the [validation checklist](../../openwiki/invariants/feature-validation-checklist.md)
carries the close-out step. A change made without a spec should run the same search before its PR.

The search is literal and cheap on purpose:

```bash
git grep -n -F "<term>" -- '*.md' ':!specs/' ':!docs/proposals/' ':!docs/decisions/'
```

This is the exact command in the tasks-template override. Keep the two identical: a change to the
override is recorded with `node scripts/check-speckit-overrides.mjs --record`.

Each hit becomes a named doc task, or gets a one-line reason it needs no change. Dated records
("measured on …", incident logs, version history) are history and need no change. A hit in a
`docs/superpowers/` design record is history too. The search covers
`openwiki/` and `AGENTS.md` too, so a renamed path or flag is also caught in the wiki and the index.

## Upgrading Spec Kit

The override that carries the sweep is one of several Spec Kit customisations. All of them, the gate
that keeps them (`scripts/check-speckit-overrides.mjs`), its failure codes and the upgrade procedure
are in [spec-kit.md](spec-kit.md#upgrading-spec-kit).

## The quarterly drift audit (layer 3)

The audit measures whether layer 1 works. It is a backlog item that files its own successor, so the
cadence needs no scheduler and no standing owner. The session that closes one audit opens the next.

**Scope**: every doc that states current procedure: `docs/runbooks/**`, `docs/templates/**`,
`openwiki/**`, `AGENTS.md`, the root `README.md` and any project README. **Not**: decision records
(`docs/decisions/`), `specs/`, `docs/proposals/`, `docs/superpowers/`, or dated records inside any doc.
Those describe the past and stay as written.

**Procedure**:

1. **Branch from `main`**, and note the commit you read against.
2. **Read in chunks by area**, one at a time, for example CI and PR tooling, the backlog, Spec Kit,
   then the wiki and the index.
3. **Verify only checkable claims** against the tree: file and directory paths, commands, Nx
   `project:target` names, script names and flags, environment variables, workflow and job names,
   versions and pins, and links.
4. **Edit only what is proven wrong**, with the smallest edit that makes it true, and cite the
   evidence in the commit. Prefer citing the pin file to restating a version.
5. **Report what cannot be proven**, for example claims about the live runner, the forge or an
   upstream tool. List them in the PR as suspected drift rather than editing them.
6. **Code comments** found stale are outside the docs' scope. File them as one backlog item.
7. **Refresh the wiki in the same PR** for every page whose `resource` the audit changed (see the
   [wiki maintenance page](../../openwiki/process/wiki-maintenance.md)).
8. **Record the measure** in the audit log below: lines read, proven drift fixed, and the rate per
   1,000 lines. The rate is expected to fall from one audit to the next.
9. **Check for layer 2**: would a `describes:` link have caught any of the drift, on a feature whose
   sweep ran? If so, layer 1 is not enough. File layer 2 as a `status/needs-spec` item.
10. **Re-read the register of unenforced rules**
    ([`openwiki/invariants/unenforced-rules.md`](../../openwiki/invariants/unenforced-rules.md)).
    Remove each entry whose gate has landed, and add every rule the audit found stated but unchecked.
11. **Refresh the learnings ledger** ([`docs/BELAY-Learnings.md`](../BELAY-Learnings.md), following its
    [How to update](../BELAY-Learnings.md#how-to-update)). Rewrite Part 1, the story, in place. Append any lesson
    the audit paid for to Part 2, changing only the status of a lesson it reversed. Then, **from a full clone** (a
    shallow one cannot count commits), append a column to Part 3:
    `node scripts/count-repo-metrics.mjs --rev <the commit you read against> --append-log docs/BELAY-Learnings.md`.
    Never type a number into that table, and never edit an earlier column or lesson. That table is the
    repository's size and shape over time; it is a different table from this runbook's own **Audit log** below,
    which records drift rates.
12. **File the next audit, then close this one.** Use `node scripts/backlog.mjs create`, with the
    title `Drift audit YYYY-MM (quarterly, layer 3 of doc-drift prevention)` about three months on,
    labels `type/chore` and `priority/p2`, and this procedure as its acceptance criteria. Then close
    the current item.
